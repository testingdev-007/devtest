Hour 1 Intro + Bug Fixing
0:00–0:10 Welcome & Setup 10 min
"Today you're going to build a real feature for a banking app — from idea to working demo — in about three hours. We'll start by doing what every developer does before writing new code: fix what's broken."

Actions:

  • Share the repo URL on screen — participants follow the participant guide to get into their Codespace
  • While people set up, run the ice breaker out loud: "What's one thing that annoys you about your bank app or a payment app you use?"
  • Pair people up — mix ages where possible. Older participants naturally mentor younger ones and Copilot levels the playing field significantly
0:10–0:25 What is GitHub Copilot? 15 min

Goal: Show them the two main interaction modes before they need to use them. Do this yourself on screen — live demo, talking through it.

1. Inline suggestions — Type a comment and let Copilot complete it:

// calculate the interest on a savings account balance

Pause. Watch Copilot suggest. Press Tab to accept. Say: "It read my comment and wrote the code."

2. Copilot Chat — Open the chat panel. Ask "What does this function do?" then ask "Can you rewrite this so a 12-year-old could understand it?"

"Copilot is like a very fast autocomplete that has read most of the internet. It is not always right. Your job is to be the one who understands the problem — Copilot helps you write it faster."
Timing
Keep this to 15 minutes. Don't over-explain — they'll learn by doing.
0:25–0:35 Bug Tutorial — everyone together 10 min

Put how-to-find-fix-bugs.html on screen (or have everyone open it). Walk through the worked example together — a made-up bug, not one of the real 10 — so everyone sees the exact method (Look → Use → Read → Fix → Test) before touching the real dashboard.

Why a shared tutorial first
This isn't a spoiler — the worked example is deliberately fake. It means every student starts the real hunt already knowing the technique, rather than guessing at a method while also hunting for bugs.
0:35–0:55 Independent Bug Hunt 20 min

Now they apply the same method to the real dashboard. Put the bug hunt brief on the projector (bug-hunt-screen.html) and step back.

The brief (on screen)
"The NovaPay dashboard has bugs hidden across the HTML, CSS, and JavaScript. Find and fix as many as you can. For each one: write down what was wrong, how you found it, and what you changed."

The 10 bugs by difficulty:

#LevelWhat's wrong
1–3EasyMissing div tag, invisible balance, coffee shop shown as credit
4–6MediumWrong input type, button typo (onlick), withdrawal adds money
7–9HardElement ID typo, NaN on empty input, wrong interest formula
10StretchNo overdraft protection

See facilitator-reference.html for the full answer key and exact fixes.

Age handling:

  • 12–13s: Aim for bugs 1–6 with Copilot Chat helping them navigate
  • 17–18s: Push for bugs 7–10 and ask them to write the fix before checking what Copilot suggests
0:55–1:00 Share Out 5 min

Ask 2–3 people or pairs: "What did you find?" and "How did Copilot help you — or did you find it yourself first?"

"That's the debugging loop — notice something's wrong, investigate, fix, test. Copilot speeds up the middle part, but you're still the one running the loop."
Hours 2–4 Build a Bank Feature
1:30–1:50 Quick Feature Tutorial — everyone together 20 min

Before anyone brainstorms their own idea, everyone builds the same thing once: a Savings Goal Tracker, from an empty starter file, following how-to-build-your-feature.html step by step. This teaches the actual fundamentals — comment, Tab, save, test, repeat — on a guided, low-stakes example.

Why build something before brainstorming
Students who've never done this before freeze on a blank page with an open-ended idea. Doing one guided build first means the brainstorm and creation phases start from confidence and a working method, not from zero.
1:50–2:05 Brainstorm 15 min
"You've just seen a pretty basic bank dashboard. You've all used or heard of banking apps. What would actually be useful — especially for someone your age?"

Run as an open shout-out or use a shared Google Doc / Jamboard. Give them 5 minutes to add ideas, then group them.

Categories to seed if it's quiet: Things to help you save money · Things to help you understand where it goes · Things to help you plan ahead.

Back-pocket feature ideas:

FeatureDifficultyGood for
Savings Goal Tracker⭐⭐Any age — visual, tangible, scales well
Spending Category Cards⭐⭐Any age — mostly HTML/CSS
Currency Converter⭐⭐Any age — clean JS logic
Budget Planner⭐⭐⭐Mixed — income minus expenses
Round-Up Savings Calculator⭐⭐⭐Good for showing compounding
Loan Repayment Calculator⭐⭐⭐⭐Better for 17–18s
Fraud Alert Simulator⭐⭐⭐17–18s — logic heavy
Recommended default
You've just built a Savings Goal Tracker in the tutorial — so that one's off the table for this part, on purpose. If a group is stuck, point them at Spending Category Cards or Currency Converter instead — similar difficulty, genuinely different idea.
2:05–2:15 Plan 10 min

Each group sketches on paper or a shared doc. Four questions to answer:

  1. What does it do? One sentence.
  2. What does the user see? Boxes on paper — don't code yet.
  3. What are the inputs? e.g. goal name, target amount, current savings.
  4. What does it output? e.g. progress bar, percentage, time to reach goal.

Model it yourself first — spend 2 minutes doing it out loud for the Savings Goal Tracker, then let groups do their own.

"I want to build a savings goal tracker. The user types in: what they're saving for, how much they need, how much they've saved so far. It shows a progress bar and tells them how much is left. That's it — no login, no database, just a page that works."
2:15–3:35 Feature Creation 80 min

Groups build their own idea in Codespaces — this is different from the shared tutorial they already completed. Put milestone-screen.html on the projector and leave it there — it has a built-in timer and Copilot tips by year group. Y9–Y10 can still lean on starter-template.html patterns from the tutorial; Y11+ work from blank.

MilestoneTarget timeWhat it means
🏗️ HTML structure done2:40Page has the right sections and inputs — even if unstyled
🎨 Styled + basic JS working3:15Looks reasonable and does something when you interact
✨ Polish / stretch feature3:35Add one extra: validation, animation, or a second feature

Copilot prompting tips to put on screen:

✅ "Write a function that takes goalAmount and savedAmount
    and returns the percentage complete"
✅ "Add a progress bar that fills based on the percentage variable"
✅ "Validate the input so users can't enter a negative number"

❌ "Make a savings tracker"   (too vague)
❌ "Fix my code"              (no context)

Stretch goals for 17–18s who finish early:

  • Save the goal to localStorage so it persists on refresh
  • Add multiple goals
  • Add a date field and calculate how much to save per week
  • Add a "simulate a transfer" button that updates the saved amount

Your role: Circulate, don't hover. Key question to ask any group: "What problem are you trying to solve right now?"

3:35–3:45 Feature Testing 10 min

Code freeze. Everyone opens feature-test-plan.html and tries to break their own feature on purpose before showing it to anyone — empty fields, negative numbers, huge numbers. Fix anything that genuinely breaks; log the rest.

Then, once tested, each group prepares a 2-minute walkthrough. Three questions to answer:

  1. What does it do? Show it working.
  2. How did Copilot help you? One specific example.
  3. What would you add if you had another hour?

No slides needed. Browser + voice is fine.

3:45–4:00 Show & Tell 15 min

Each group demos (2 min each). After each one ask: "What did you like about that?" and "What would you add?"

Your closing (2–3 minutes):

"Today you went from a bug-ridden page to a working feature — starting from nothing except an idea. The way you worked today is genuinely how it's done in real development: pick a problem, sketch a solution, build incrementally, test it, demo, get feedback.

Copilot didn't build it for you. You told it what you needed, you checked whether it was right, and you made the decisions. That skill — knowing what to ask and whether to trust the answer — is exactly what makes a good developer."
Facilitator Notes
Note Running Solo
  • Have group instructions visible at all times — on screen, in a shared doc, or both. You can't be everywhere at once.
  • Use the milestone board (whiteboard or shared doc) to keep groups on track without you narrating constantly.
  • Build in one check-in at 2:15 — ask each group to say one sentence about where they are. Helps you spot who's struggling before it becomes a crisis.
Note Handling Mixed Ages
  • Pair 12–13s with 17–18s where possible. Older students who explain something to a younger one learn it better themselves.
  • Same feature, different depth. Both ages can build a savings tracker — the 13-year-old makes it work, the 18-year-old adds validation and localStorage.
  • Copilot Chat is a great leveller — younger students can ask it to explain code in plain English.
